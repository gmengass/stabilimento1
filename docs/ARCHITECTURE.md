# Architecture

> High-level map of the system. Update it when structure changes. Details belong in ADRs.

## Overview
One web app and one PostgreSQL database on a local server at the club, reachable only from the
staff Wi-Fi (and optionally Tailscale), with nightly encrypted backups to OneDrive (ADR 0003).
Single venue with one or more booking areas. 5–10 staff users; changes appear on other staff
screens within seconds. Customers never use the app. They are contact details on a booking.

## Core domain (stack-independent)
- **Venue**: the beach club (exactly one for now; modeled as a table so it isn't hard-coded)
- **Area**: a bookable zone within the venue (e.g. main beach, second area), with its own layout. Adding an area is a data change, not a code change.
- **Line** (table `area_line`): area, number (1 = closest to the shore)
- **Spot**: area, line, number (what staff call it, unique per area; default line × 100 + position), position (order in the line, 1 = leftmost facing the sea), kind (umbrella | sunbed), included_sunbeds (default 2), max_sunbeds (default 3)
- **User**: a staff login (Better Auth, ADR 0007). id, username, name, role (admin | staff),
  banned (= disabled), locale (it | en). Plus Better Auth's `session`, `account`, `verification`
- **Customer**: name, optional phone, email and notes (no login)
- **VenueSettings**: default_hold_until (11:00), time zone (Europe/Rome)
- **SpotClosure**: spot, date range, reason (maintenance, reserved by the club)
- **Season**: venue, name, start_date, end_date. One season per calendar year, covering every
  beach space, so a day belongs to at most one season. The next season can only be added once
  the current one has ended
- **Booking**: customer, kind (day | multi_day | season), start_date (a season pass's first day),
  end_date (inclusive local dates), season, status, notes, hold_until (optional override)
- **BookingSpot**: booking, spot, sunbeds (how many go with this umbrella)
- **SpotDay**: spot, date, booking_spot, state (booked | released | no_show). Unique per (spot, date)
  while occupied (ADR 0004)
- **CheckIn**: booking, date, checked-in time, staff user
- **AuditLog**: user, action, booking, before/after, timestamp
- **Payment** (later): booking, amount, method (cash/card at desk), staff user

## Invariants
- A spot can be occupied by at most one booking per day. This is enforced in the database
  (unique (spot, date) on SpotDay), not only in application code.
- Booking days are local calendar dates (`Europe/Rome`); timestamps are stored in UTC (ADR 0004).
- Status changes go through a single service function so they can be audited.

## Directory layout
- `src/app/`: Next.js routes (App Router), incl. `/health`
- `src/lib/`: shared code (`env.ts` validates environment variables)
- `src/lib/auth/`: Better Auth config (`auth.ts`), `session.ts` (`getCurrentUser`, `requireUser`,
  `requireAdmin`), `staff.ts` (admin account management), `rules.ts` (username/password rules)
- `src/app/(app)/`: everything behind login; `src/app/login/` is the only public page.
  `/api/auth/*` forwards an allowlist to Better Auth (ADR 0007)
- `src/db/seed-admin.ts`: creates the first admin (`npm run db:seed-admin`, allowed in production)
- `src/db/client.ts`: Kysely client; `types.ts` is generated by `npm run db:types` (never hand-edit)
- `src/db/migrations/`: numbered migrations, each with `up` and `down`; run by `migrate.ts`
- `src/db/seed-data.ts`, `seed.ts`: idempotent demo seed (`npm run db:seed`, refused in production)
- `src/i18n/`: next-intl setup (ADR 0005): `config.ts` (locales), `resolve-locale.ts`, `request.ts`,
  `actions.ts` (`setLocale`), `format.ts` (booking days, Rome timestamps, EUR)
- `src/components/`: shared UI (`language-switcher.tsx` in the root layout header)
- `messages/it.json`, `messages/en.json`: all UI text; a unit test enforces key parity
- `tests/unit/`, `tests/integration/`: Vitest; integration tests only touch a `*_test` database
- `e2e/`: Playwright specs (`npm run test:e2e`, builds and starts the app)
- `deploy/Caddyfile`: HTTPS (internal CA) and the `X-Real-IP` header the app trusts (ADR 0008)
- `scripts/update.sh`, `rollback.sh`, `pre-update-backup.sh`, `setup-wsl.sh` (one-time box setup):
  POSIX sh deploy scripts; operator steps
  in `docs/RUNBOOK.md`

## Authorization
- Every page, Server Action and route handler checks the user itself (`requireUser`,
  `requireAdmin`, or `readCurrentUser` in actions). Layout guards are not a security boundary.

## Rendering
- The root layout reads the `locale` cookie, so it sets `export const instant = false` (ADR 0006) and every
  route renders per request. Fine for a staff-only LAN app; revisit if a static page is ever needed.
